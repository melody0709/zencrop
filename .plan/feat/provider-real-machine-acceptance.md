## 0. 通用约定

1. **每条 S 项都带同一个对照项**：动作以 **Cancel / ESC** 收尾后，`settings.json` 的 `translation` 段**逐字节不变**（唯一例外见 S6）。
   证据取法：执行前后各记一次文件哈希（`Get-FileHash settings.json -Algorithm SHA256`），并在有改动时附 `git diff --no-index` 片段。**"界面上看着没变"不算证据**——写盘是这一层最容易漏的回退。
2. 每条记录必须写清：**用的 provider、模型 id、key 属于哪一个档案**。结论绑在具体模型上，不能跨厂商推广（F12 的结论绑在 `gemini-3.8-flash` 上就是例子）。
3. 记录"失败"时不要只写结论：把厂商的 `error.message` **原文**贴进来（这是 F11/F13 唯一有效的定位手段）。
4. 只有在两项都签收、且 §11 里登记的遗留项都被显式接受之后，才考虑提交与版本提升。

## 1. 模型选择器（`Manage models`）

对照项（每条都要做）：动作后 Cancel → `translation` 段哈希不变。**S6 例外**。

| :-- | :-- | :-- | :-- |
| S1 | 抓取 OpenRouter（当前最大清单 458 行）后滚动到末尾、搜索、勾选若干 | **耗时与流畅度**：清单重建无可见卡顿（记录滚动全程是否出现白屏/逐行跳出），勾选响应 < 100ms 量级 | 判据不是"能滚"——能滚是必然的。要的是"重建/过滤不随行数退化" |
| S2 | 池已有 50 个时勾第 51 个 | ① 出现拒绝提示；② **Cancel 后池内容与顺序逐字节不变**；③ 本次操作 FIFO **一次都没触发**（对比前后池的首尾元素） | 真风险不在文案，而在"拒绝了但池已经被改"。FIFO 静默淘汰是这条的两个失败面 |

| S4 | 在 `Add` 里手输一个**内置种子 id**（例如 `gemini-3.8-flash`） | 看到"内置目录模型不需要收藏"类提示 **且列表里没有插入新行** | 只验提示会漏"插入了行但没入池"的中间态 |
| S5 | 过滤（搜索）后点 `Set active` | ① 活动 id 在过滤结果里可见时：设置成功、提示行显示该模型；② **活动 id 不在抓取清单里时**：保持不变（不因过滤/清单变化被清空或改写） | 陷阱是"活动 id 被过滤隐藏"——只验可见那遍会给假通过 |
| S6 | 打开选择器 → Cancel | **明确预期**：`FinishModelFetch` 在打开对话框**之前**就已写入 `modelCatalogFetchedAt` 与本次学到的显示名（`TranslationProviderSettingsPage.cpp` 的抓取收尾，注释写明了这是有意为之）。所以"Cancel 什么都不做"是**错的**预期。要通过必须：除这两项外没有别的改动（时间戳更新 + 显示名侧表写入属预期，其余任何差异都是缺陷） | 这条最容易被报成 bug。清单要把它写成预期行为，否则会被当成回归处理 |
| S7 | 系统 DPI 调到 200%，抓取一份厂商名很长的清单（OpenRouter），并看一遍 Provider 页整体几何 | **现在定判据**：① `Display name` 列**允许裁切**，但必须"可读"——id 列完整可辨、被裁切的行能通过悬浮/提示看到全名；② 三列的宽度按**列表自身宽度**分配（约 53% / 26% / 21%，随 DPI 与字体缩放），**不允许**出现"列只占左侧一小条、右边大片空白"（那是固定像素列宽在 200% 下的症状）；③ **不允许出现底部横向滚动条**——尤其是"只能拖十几二十像素"的那种：列宽之和必须小于列表客户区（垂直滚动条出现后会占掉约 17 px，200% 下 34 px），这是列宽按"无滚动条时的宽度"布局会踩的坑；④ Provider 管理窗的 `Name:` 行：`Reset profile` 与 `Delete` 分别落在 **232 / 268** 两列（各按钮右边缘与 `Add` / `Restore defaults` / `Models…` 和 `Copy` / `Test connection` / 所有整宽字段对齐），**标签不得裁切**；⑤ `Name` 编辑框已收窄到 104 DLU，长显示名（如 `Microsoft Translate Community`）在框内会横向滚动——**这是刻意的**，文本不丢、Apply 读到的仍是完整值 | 若判据写成"不裁切"（列宽），这条必然失败并变成无意义的返工；`Name` 框的滚动若被当成缺陷会引来一次错误的"再放宽"（放宽就得牺牲 `Reset profile` 的宽度，即回到标签被裁切的状态）。真正要验的是"信息可得 + 列宽随 DPI + 无横向滚动条 + 按钮标签完整 + 两列对齐"。第 ③ 项只在**行数超过可视高度**时才会出现（几百行），用短清单验不出来 |
| S8 | 用 IME 在 `Add` 与页面 Model 字段里输入 **全角空格**（U+3000）与不换行空格（U+00A0），提交 | 提交前后都验：`Add` 里被拒且有文案；页面 Model 字段在键入时状态行给出提示，Apply 被拒（不是被静默改写） | `?`/半角空格的文案已有用例；要验的是 **IME 提交路径是否绕过谓词**（IME 的组字提交可能不走 `EN_CHANGE` 的预期序列），以及 disabled 档案上 Apply 是否也拒绝 |

## 2. Gemini OpenAI 兼容面（三个探针 + 一条决策）

方法比结论重要：**必须用引擎实际构造的 body**，不要手写近似值（F11 与 F13 都是手写近似值放过的）。

| # | 探针 | 记录什么 | 失败/结论处理 |
| :-- | :-- | :-- | :-- |
| G1 | `POST /v1beta/openai/chat/completions`，body 带 `response_format: {type: "json_schema", json_schema: {strict: true, schema: <引擎的那一份，含 id 枚举>}}` | HTTP 状态 + `error.message` 原文（若有） | 4xx 即失败：把原文贴进本节；结论是"兼容面不支持 `json_schema` 形态" |
| G2 | 同一路径，`response_format: {type: "json_object"}` | 同上 | **若 G1 4xx 而 G2 200**：结论是该协议需要在协议表上补一个 `outputMode` 能力位——方案 §11.5 里"等实测"的第 ③ 条立刻变成可执行项，而不是继续挂着 |
| G3 | `GET /v1beta/openai/models` | 状态码、原始 JSON 头 200 字符、实际发送的认证头名（`Authorization` 还是 `x-goog-api-key`） | 抓取路径**完全未实测**；形状不符时按 `ModelListProtocol::OpenAiData` 的容错范围评估是否需要新信封 |
| G4 | **基址写错**（例如 `https://generativelanguage.googleapis.com/v1beta/openai/typo/`） | 记录状态行实际显示的内容 | **已知可接受**：Google 对未知路径返回 `text/html`，`ProviderErrorDetail` 取不到文案 → 状态行只有 `(404).`。这正是本轮重构最初的用户可见症状：重构治了**成因**，没治这个**症状**。写在这里是为了将来有人报上来时它是**决策**而不是回归 |

**不必重测**：兼容面的思考档位（`none`/`low`/`medium`/`high` → 200、`minimal` → 400）已用真实 key 实测过；但该结论**绑定在 `gemini-3.8-flash`** 上，换模型或推广到原生面要重新记录模型 id。

### 2.1 G1/G2 样本的生成方法（**不得手写**）

手写近似值是 F11 与 F13 两次误判的共同成因，所以样本必须由**引擎自己**产出。仓库里已有现成接缝：

| 步骤 | 做法 |
| :-- | :-- |
| 1. 生成 | 临时在 hermetic 测试目标 `test_translation_contract` 里加一段打印（它已链接引擎 TU，并有 `CaptureTranslationTransport`），用既有的 `WireProfile(...)` + `RunCapturedProvider(profile, response, call)` 取到 `call.url` / `call.headers` / `call.body`；跑 `tests\build_and_run.bat test_translation_contract` |
| 2. 落盘 | 样本与（真实发出去后的）响应原文放 `build/artifacts/diagnostics/`；**抓完删除临时代码**，随提交一起消失 |
| 3. 发送 | 用样本里的 URL + body（+ 头名对应的真实 key）发出，只把响应原文填回本节 |
| 4. 对照 | 响应若成功，另跑一次 G2 的 `json_object` 变体；把两份 body 的**差异行**一并记下（差异应该只有 `response_format` 那一行） |

**三个必须先定的坑（否则样本是假的）**：

1. **body 依赖 settings，不只是 profile。** `BuildRequestBody(settings, …)` 里的 `ComposeTranslationPrompt` 读的是**当前 prompt profile**，段数与段文本也进 body。`RunCapturedProvider` 的默认 settings 用的是 `builtin.accurate.v1` + **1 段**（`s1` = `Hello`，en→zh-Hans）——样本必须**同时声明**这三项（prompt profile id、段数、段文本）；要改就通过 `customRequest` 显式给（多段/长段/带换行），不能"形状对了就行"。
2. **profile 必须钉死。** `gemini` + **显式** `adapterKind = OpenAIChatCompletions`（`WireProfile` 默认给的是原生面）+ `authMode = BearerApiKey`（兼容面要 Bearer）+ `model = gemini-3.8-flash` + 思考档位 **`Off` 与 `ProviderDefault` 各一份**（G1 至少要 `Off`：那才是会带 `reasoning_effort` 的形态）。换模型 id 或换档位要重新记结论。
3. **证据与密钥。** 样本里**不得出现真实 key**：`headers` 只记**头名**，G3 另外记录实际头名；响应原文可以整段贴（厂商不回显 key）。
4. 时效：样本从**当次提交的代码**生成；验收前若又改了引擎或策略表，样本必须**重新生成**，否则"逐字节可比对"不成立。
